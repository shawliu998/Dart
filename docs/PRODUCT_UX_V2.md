# 标证通 Product UX V2

## 1. 问题与设计目标

标证通服务的核心任务不是“与 AI 对话”，而是把招标文件转化为可追踪、可复核、可交付的项目工作。现有项目总览、要求矩阵、证据匹配、一致性检查、整改任务、封装和审计仍是主工作面；V2 新增的 Agent 运行中心只负责解释确定性工作流正在做什么、卡在哪里、需要谁批准、产出了什么。

V2 解决四类体验问题：

1. 用户看得到业务结果，却不容易理解一次跨模块运行的先后关系和当前阻塞。
2. API、演示数据和加载失败如果混在一起，会让演示结果被误认为生产结果。
3. AI 候选、确定性规则结果和人工决定容易在视觉上混淆。
4. 审批入口分散；用户需要知道影响、可逆性和原文来源后，再进入对应业务工作台处理。

成功标准：用户在 30 秒内能回答“这次运行因何触发、目前在哪一步、有哪些人工门禁、哪些输出可用、重要结论来自哪里”，且不会把 Agent 运行中心误当成最终裁决或外部提交工具。

## 2. 产品原则

- 工作台优先：要求、证据、风险、任务和封装页面承载业务决策，Agent 页面不复制复杂编辑能力。
- 来源优先：重要结论同时显示文件、页码、摘录、置信度或规则状态。
- 人在回路：低于 0.70 的模型结果、阻断项、证据接受、补充公告高影响变更和最终包生成进入人工门禁。
- 确定性计算：金额、日期、数量、阈值、最终合规状态和封装阻塞由规则服务计算，不交给模型。
- 状态诚实：API、演示和失败是三个互斥状态；失败不会静默降级成演示。
- 审计默认：模型版本、Prompt 版本、规则版本、输入输出和人工更正进入追加式审计。
- 不做越权自动化：不自动给出法律资格结论，不执行 CA 签名、保证金支付、验证码绕过或无人值守外部提交。

## 3. 信息架构

```text
工作空间
├── 工作台 / 项目组合
├── 投标项目
│   ├── 项目总览
│   ├── 招标要求
│   ├── 否决项
│   ├── 证据匹配
│   ├── 一致性检查
│   ├── 补充公告
│   ├── 整改任务
│   ├── 文件封装
│   └── 审计记录
├── 企业材料库
└── Agent 运行中心（辅助视图）
    ├── 运行摘要
    ├── 步骤时间线
    ├── 人工审批队列
    └── 运行输出
```

路由 `/agent` 默认展示演示项目的最近一次运行。运行中心中的操作均为真实导航：要求审批进入要求工作台，证据审批进入证据匹配，封装审批进入文件封装。运行中心本身不提供“看似批准但没有持久化”的按钮。

## 4. 状态模型

### 4.1 运行状态

`queued → planning → running → waiting_approval → running → completed`

异常分支为 `failed`，用户主动停止为 `cancelled`。业务阻塞不是额外的 Run 状态：步骤用 `blocked`，风险输出用严重度，Run 在有人工作时为 `running`、等待人工时为 `waiting_approval`。

### 4.2 步骤状态

- `pending`：尚未达到执行条件。
- `running`：当前正在执行确定性服务或受控模型适配器。
- `completed`：产出已写入运行记录，不代表业务结论自动成立。
- `blocked`：缺少人工批准、前置数据或规则未通过。
- `failed`：步骤执行异常，需要查看错误并重试整次聚合或业务步骤。

### 4.3 审批状态

`pending | approved | rejected`。审批类型限定为 `evidence_match | compliance_override | consistency_resolution | amendment_apply | package_warning | package_build`。审批卡必须显示描述、影响摘要、是否可逆、所需角色和来源。V2 的 `/agent` 只把用户送到拥有完整上下文和审计能力的业务工作台。

### 4.4 数据来源状态

- `api`：所有所需聚合端点成功返回，页面展示 API 数据标识。
- `demo`：没有配置远端 API，明确展示“本地确定性演示”。
- `failure`：配置了 API 但任一聚合请求失败；显示错误、重试和“显式打开演示”选项，不自动替换。

## 6. 组件规范

- `AgentWorkspace`：接收判别联合 `AgentDataResult<AgentRunBundle>`，处理 API、演示、失败和显式演示切换。
- `RunSummary`：标题、目标、状态、进度、项目、触发原因、发起人、版本和安全边界。
- `StepTimeline`：使用有序列表；图标外必须有文字状态，不能只靠颜色。
- `ApprovalQueue`：显示影响、可逆性、角色、来源和真实业务路由；不在这里伪造批准。
- `OutputGrid`：展示可操作输出、数量、严重度和来源；卡片链接到已有工作台。
- `SourceReference`：统一呈现“文档 · 页码 · 摘录 · 置信度/规则结果 · 复核状态”。
- `FailureState`：`role=alert`，提供刷新重试和显式打开演示；保留原始错误摘要。

## 7. 交互与可访问性

- 所有交互可用键盘访问，焦点样式清晰；链接与按钮语义不可互换。
- 状态同时使用文字和图形，不只依赖红/黄/绿。
- 进度使用原生 `progress` 或等价 ARIA 属性，并提供百分比文本。
- 来源摘录使用可展开内容；默认仍显示足够的文档和页码信息。
- 动态反馈使用 `role=status`，失败使用 `role=alert`。
- 运行中不使用无限闪烁动画；尊重 `prefers-reduced-motion`。

## 8. API Adapter

前端 `frontend/lib/api/agent.ts` 以现有项目端点聚合运行快照：requirements、evidence-matches、consistency、amendments、tasks、package、audit。适配器只做字段兼容、计数和 UI 运行投影，不产生业务结论，不写数据库，不调用真实模型。

聚合契约使用判别联合：

```ts
type AgentDataResult<T> =
  | { source: "api"; data: T; error: null }
  | { source: "demo"; data: T; error: null }
  | { source: "failure"; data: null; error: AgentFailure };
```

任何 API 请求失败都会返回 `failure`。只有没有配置远端 API，或用户在失败页显式选择演示时，才返回 `demo`。

## 9. 验收标准

1. `/agent` 不是聊天页，且能看到 Run、Step、Approval、Output 四类对象。
2. Run/Step/Approval 状态与 `AGENT_EXPERIENCE_SPEC.md` 一致。
3. 每项重要输出至少带一个来源引用；规则结果清楚标记为规则而非模型置信度。
4. 低置信度模型结果与阻断性候选项进入人工门禁。
5. API 失败不静默显示演示数据；显式切换后才显示演示标识。
6. 审批入口导航到可完成真实业务动作的现有工作台，不出现死按钮。
7. 页面不触发真实模型、外部提交、CA 签名或最终法律判断。
8. 组件通过 TypeScript、ESLint 和 Agent 相关 Vitest；键盘和状态文本通过组件测试。
