# 模型分工与验收约束

## 目标

在不降低 BidEvidence 安全性、可追溯性和交付质量的前提下，将边界清晰、可机械验证的工作交给快速/低成本模型，将方案、风险判断和最终验收交给强模型。节省 token 的主要手段是缩小任务与上下文，而不是降低验收标准。

## 任务选择优先于模型分工

模型分工只决定“已经选定的任务由谁执行”，不能决定“下一步应该做什么”。所有模型在选择任务前必须先读取 `docs/CURRENT_PRODUCT_PRIORITY.md`。

- 当前阶段只从竞品界面能力和核心用户工作流差距中选择任务。
- 快速/低成本模型不得自行把安全、审计、本地运行、部署、基础设施或发布加固升级为下一任务。
- 强模型发现上述问题时，若不直接阻断当前选定的产品能力，只能记录为非阻断观察，不能切换执行主线。
- 每个执行包必须增加：竞品依据、用户任务、当前可见差距、预期可见结果和截图/交互验收证据。
- 不满足产品选择门禁的任务，即使容易实现或容易测试，也不得进入执行。

## 分工边界

### 快速/低成本模型可执行

- 按明确验收条件修改单一模块、组件或脚本。
- 搜索文件、盘点路由/按钮/测试覆盖，生成结构化清单。
- 编写明确规则的 fixture、单元测试、格式化、类型修复和文档同步。
- 运行已定义命令，归纳失败日志，但不独立改变产品或安全策略。

### 强模型必须负责

- 需求澄清、产品定位、信息架构、数据模型和跨模块设计。
- 租户隔离、鉴权、审计、文件处理、依赖/许可证、数据库迁移和 AI 安全边界。
- 金额、日期、数量、否决项、合规结论、证据接受和封装审批逻辑。
- 验收条件的制定、最终 diff 审查、回归范围选择、失败归因与交付结论。

## 执行包

交给执行模型的每个任务必须只包含必要上下文，并明确：

1. 单一、可验收的目标。
2. 允许读取和修改的文件/目录。
3. 不得改变的数据契约、安全边界和用户现有改动。
4. 必须运行的验收命令及成功标准。
5. 停止并升级的条件，不得自行扩大范围。
6. 交接格式：改动文件、行为变化、测试结果、未解风险。

## 强制验收门

1. 先定义 oracle/测试/验收条件，再实现。
2. 执行模型先做自测；未提供测试结果的交付不进入验收。
3. 验收模型必须自行阅读 diff 和关键源码，不得只复述执行者的总结。
4. 验收模型至少重跑针对性测试；跨模块或发布级变更还必须跑 `make verify`。
5. UI 改动必须有实际浏览器验收；PDF/DOCX/XLSX 必须有渲染或重新打开验收。
6. 任何失败、范围溢出或不确定性都必须返回强模型；不得用“大概可以”代替证据。
7. 未经强模型验收，不得推送、合并、标记 PR ready 或改变外部状态。

## 必须升级的信号

- 需修改 API/Schema/数据库迁移或跨前后端契约。
- 涉及鉴权、租户、审计、密钥、上传文件、模型输入或人工审批。
- 涉及金额/日期/计数/最终合规结果或法律判断。
- 任务需超出执行包的文件范围，或验收条件相互冲突。
- 出现非相关工作树改动、不稳定测试、无法解释的 CI 差异或新依赖/许可证。

## Token 和并行约束

- 新任务传递“当前分支 + 基准提交 + 目标 + 范围 + 验收命令”，不复制完整历史对话。
- 先用 `rg`/定向测试定位，不得无目的地读取整仓库、整份日志或全部生成物。
- 并行任务必须拥有不重叠的文件边界；共享契约由一个主任务负责。
- 交接只传结论、diff 范围、测试和风险；已通过的长日志不重复粘贴。
- 同一问题连续失败两次后停止低成本重试，直接升级强模型诊断。

## 质量结论

低成本模型执行、强模型验收本身不会必然降低质量；影响质量的是任务是否可分解、契约是否明确、验收是否独立。对高风险或高模糊任务，应直接由强模型实现与验收，不为节省 token 强行下放。
