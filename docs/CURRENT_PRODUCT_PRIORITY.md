# 当前产品优先级与执行硬约束

## 1. 当前阶段

自 2026-07-28 起，用户已明确将当前唯一主线调整为：
**把已有竞品工作流基线封装成下载后可配置、可验证、可使用的桌面产品。**

本阶段的产品化顺序是：

1. 工作区模型设置：内置 Mock、DeepSeek、真实结构化连接测试和无重启切换；
2. 桌面包内置后端与前端运行时，终端用户无需预装 Docker、Node 或 Python；
3. 首次启动、空状态、失败恢复、数据目录和卸载/升级说明；
4. macOS 可安装产物及干净机器验收；签名、公证和自动更新单独排期。

竞品工作流和视觉基线继续保留；不得借产品化之名重做核心工作台、平行 API
或第二套设计系统。安全、审计和基础设施仍只处理本切片的直接阻断项。

## 2. 产品中心

产品中心是项目内的投标工作流，不是安全控制台、审计控制台、本地演示器或通用聊天 Agent。

当前核心路径：

```text
项目与文件接收
→ 招标要求/合规矩阵
→ 原文与来源联动
→ 企业材料和证据复用
→ 投标响应编制与人工复核
→ 整改和交付检查
```

Agent、审计、安全提示和运行环境说明只能作为辅助能力出现，不得抢占核心路径的主导航、首屏标题和主要行动按钮。

## 3. 任务选择门禁

任何开发任务开始前必须先阅读 `docs/EXISTING_CAPABILITY_MAP.md`，并写清以下六项；缺一项不得实现：

1. **竞品依据**：具体产品、公开页面、截图或仓库内参考文件。
2. **用户任务**：投标经理或复核人员要完成的具体动作。
3. **当前差距**：现有页面缺少什么可见能力，不得只写抽象技术缺口。
4. **可见结果**：用户完成任务后能看到或做到什么。
5. **验收证据**：同视口截图、真实交互、测试和明确的通过条件。
6. **复用决定**：复用哪些现有组件、API、状态和测试；真正缺少哪一层；为什么需要新增文件。

除上述下载可用主线外，若任务的主要理由是以下任一项，默认拒绝并返回产品差距清单：

- “更加安全”“更加完整”“更适合生产”但没有阻断当前用户任务；
- 增加 request id、日志字段、审计元数据或监控指标；
- 与本次桌面下载闭环无关的部署方式或开发环境扩张；
- 新建独立 Agent 页面、运行时间线或通用聊天入口；
- 清理架构、依赖、许可证或性能，但没有可复现的当前页面阻断；
- 为了覆盖 PRD 条目而增加用户无法完成真实任务的按钮或页面。

## 4. 当前能力顺序

下载可用主线完成前，按第 1 节的产品化顺序选择工作。核心工作流的后续
竞品能力仍按以下顺序排队，上一级没有明显缺口时才进入下一级：

1. 投标响应编制工作台：大纲、逐节编辑、要求/证据来源、人工复核。
2. 合规矩阵深度：筛选、批量复核、原文定位、键盘工作流、导出。
3. 文件接收和处理反馈：分类、进度、失败恢复、补充文件。
4. 企业材料库：知识复用、有效性、版本、使用项目和人工接纳。
5. 协作能力：负责人、复核人、评论/原因、状态和截止日期。
6. 交付能力：版本、预览、导出、文件清单和最终人工检查。

项目目录、Dashboard 和 Agent 运行中心只有在直接支持上述核心任务时才可修改。

## 5. 视觉和交互规则

- 复用现有 Dart 设计系统、壳层、组件和图标，不另建平行设计语言。
- 复刻的是竞品的任务结构、信息密度和交互能力，不复制竞品商标、品牌色或专属文案。
- 每个主要按钮必须完成真实动作或进入能够完成动作的页面；禁止假按钮和死路由。
- 不得用大面积安全说明、演示标识、Agent 状态或技术术语挤压主要工作区。
- 桌面工作台优先，同时保证窄屏可完成核心任务；不能仅保证页面不报错。
- UI 验收必须把参考图和实现图放在同一对比证据中，并修复 P0/P1/P2 差异。

## 6. 模型分工

- 强模型负责竞品能力判断、信息架构、跨端契约和最终视觉/功能验收。
- 低成本模型只执行已经锁定目标、参考图、文件范围和验收条件的机械实现。
- 低成本模型不得自行发现并选择“下一个重要技术缺口”。
- 任何模型发现安全、审计或基础设施问题时，只记录为非阻断观察；除非它直接阻止当前产品任务，否则不得切换主线。

## 7. 每批交付格式

每批只交付一个可独立验收的竞品能力切片，并报告：

- 复刻了什么能力；
- 用户现在能完成什么任务；
- 参考证据和实现截图；
- 实际交互和测试结果；
- 仍缺少的下一项竞品能力。

不得以安全项数量、审计字段数量、测试数量或架构完整度代替产品能力结论。
